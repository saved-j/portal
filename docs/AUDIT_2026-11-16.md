## Находки

### B1 — engine-sweep переживает отмену и может выключить новый портал

**Evidence.** Listener режима делает только `cancel()` и обнуляет
`runningSweep` в [lib/views/dashboard/portal_controls.dart:1116-1120](../lib/views/dashboard/portal_controls.dart).
Но `_testDelayWithEngine` не читает ни `_generation`, ни `runningSweep`:
после `setRunning(true)` он ждёт до 6 секунд ([1486-1491](../lib/views/dashboard/portal_controls.dart)),
вызывает delay API ([1560-1561](../lib/views/dashboard/portal_controls.dart)) и без
повторной проверки состояния в `finally` делает `setRunning(false)`
([1562-1565](../lib/views/dashboard/portal_controls.dart)). В отличие от child
пути, engine-путь также не выставляет собственный sweep-token.

**Почему это важно.** Последовательность воспроизводима: список Rule запускает
автоматический sweep при закрытом портале; пользователь переключается в Simple
portal и открывает Xray; старый engine-sweep завершается и его
`setRunning(false)` закрывает текущий владелец туннеля. Координатор корректно
сериализует отдельные транзакции, но не знает, что поздний `setRunning(false)`
принадлежал измерению, а не текущему владельцу. Результат — потеря соединения
и возможное отображение задержек уже неактуального списка.

**Suggested fix (L).** Ввести единый монотонный `SweepSession` (id, profileId,
mode, owner, cancellation token) для обоих путей. Проверять его до/после
каждого await и особенно перед `delayTest`, `record` и закрытием поднятого
временно owner. Закрывать только ресурс, открытый этой же session и только
если runtime-generation/owner всё ещё совпадают. Добавить widget/integration
test: Rule sweep → mode switch → Xray open; assert, что второй туннель не
закрыт.

**Effort:** L.

### M1 — отменённый child-sweep снова становится «текущим»

**Evidence.** Child-sweep назначает id как `(delay.runningSweep ?? 0) + 1`
([lib/views/dashboard/portal_controls.dart:1617-1618](../lib/views/dashboard/portal_controls.dart)),
а при смене режима listener делает `runningSweep = null`
([1116-1120](../lib/views/dashboard/portal_controls.dart)). Новый sweep получает
id `1`, как и старый. Старый после возврата native-вызова считает себя текущим,
так как проверяет лишь равенство ([1647-1650](../lib/views/dashboard/portal_controls.dart)),
записывает строки ([1660-1667](../lib/views/dashboard/portal_controls.dart)) и
может обнулить `runningSweep` нового sweep в `finally` ([1675-1677](../lib/views/dashboard/portal_controls.dart)).

**Почему это важно.** Обещание патча 43 «cancelled sweep does not write rows»
не выполняется. Одинаковые имена узлов в двух списках особенно опасны: старый
ответ будет выглядеть правдоподобно и останется свежим 2 минуты.

**Suggested fix (M).** Никогда не сбрасывать token в `null` как способ
отмены. Держать отдельный неубывающий `nextSweepId`; `cancel()` только
инкрементирует его. Перед каждой записью проверять token плюс profile/mode.
Покрыть тестом interleaving «A запущен → cancel → B запущен → A отвечает».

**Effort:** M.

### M2 — профиль не является частью состояния задержек

**Evidence.** `TcpDelayNotifier.build()` только watch-ит profile и возвращает
пустой `state`; полевые `measuredAt`, `runningSweep` и `_generation` не
сбрасываются ([lib/views/dashboard/portal_controls.dart:182-211](../lib/views/dashboard/portal_controls.dart)).
`_generation` увеличивается лишь в `cancel()` ([330-335](../lib/views/dashboard/portal_controls.dart))
или при dispose, а не при смене зависимости. Свежесть определяется только по
имени узла ([194-199](../lib/views/dashboard/portal_controls.dart)).

**Почему это важно.** После profile switch старый native-ответ может записать
одноимённый узел нового профиля. Даже без in-flight ответа одноимённый узел
будет ошибочно считаться свежим и не измерится. Это нарушает комментарий о
profile-bound cache и может показывать чужую задержку.

**Suggested fix (M).** Внести `profileId` в ключ измерения или при изменении
profile atomically отменять session, инкрементировать token и очищать state +
`measuredAt`. Перед `record` сверять id профиля, захваченный при старте.

**Effort:** M.

### M3 — native timeout не ограничен сверху

**Evidence.** Dart передаёт константу 8000 мс
([lib/views/dashboard/portal_controls.dart:1710-1717](../lib/views/dashboard/portal_controls.dart)),
но native `MeasureTags` подменяет только `<= 0` и не имеет max для
`timeoutMs` ([`/Users/saved/.hermes/cache/scratch/xraylib/build/libxray/measure.go:112-123`](file:///Users/saved/.hermes/cache/scratch/xraylib/build/libxray/measure.go)).
Напротив, `limit` ограничен 32. Каждый worker создаёт HTTP client с этим
timeout ([192-204](file:///Users/saved/.hermes/cache/scratch/xraylib/build/libxray/measure.go)).
Kotlin ставит измерение в единственный executor ([XrayPlugin.kt:134-145](../android/app/src/main/kotlin/com/follow/clashx/plugins/XrayPlugin.kt)),
а `Future.cancel(true)` при таймауте не обязан прервать JNI/Go-вызов
([136-140](../android/app/src/main/kotlin/com/follow/clashx/plugins/XrayPlugin.kt)).

**Почему это важно.** Положительный `Int` до 2_147_483_647 мс даёт почти
24.9 суток. В это время single executor задерживает stop/start child и
отменённый sweep может удерживать до 32 goroutines. Хотя обычный UI передаёт
8000, boundary native API должна быть безопасна сама по себе.

**Suggested fix (M).** Clamp `timeoutMs` до документированного max (например,
8–15 s) *до* запуска instance, ограничить tags/config size, и передать в Go
явный cancellation context, который `XrayMeasureStop` отменяет, а не только
закрывает instance. Добавить native tests для negative/huge timeout и
конкурентного stop.

**Effort:** M.

### M4 — release-конфигурация не fail-closed

**Evidence.** pubspec несёт `0.5.6+2026111601` ([pubspec.yaml:4](../pubspec.yaml)),
local.properties — `0.5.6`/`2026111601`, но Gradle строит code как
`flutter.versionCode + 5000` и default versionName
`0.5.6_1a-portal-duo` ([android/app/build.gradle.kts:53-60](../android/app/build.gradle.kts)).
Если `keystore.jks` либо любое из трёх свойств отсутствует, release получает
debug signing и suffix `.dev` ([17-24](../android/app/build.gradle.kts),
[98-110](../android/app/build.gradle.kts)), без ошибки. В проверенной рабочей
копии `android/app/keystore.jks` отсутствует.

**Почему это важно.** Релизный task может выдать технически release APK, но с
неожиданным identity/applicationId и версией. Это затрудняет обновление,
диагностику и доставку владельцу.

**Suggested fix (S).** Для release требовать signing material через Gradle
`GradleException`; debug/pre сделать отдельным явно названным variant/task.
Единым source-of-truth выбрать pubspec или CI build metadata и assert-ить
совпадение `versionName`, `versionCode`, package suffix и ожидаемого
сертификата в CI.

**Effort:** S.

### m1 — диагностические логи раскрывают данные подписки/маршрутизации локально

**Evidence.** Telemetry намеренно пишет в app external files, читаемые через
adb ([android/common/src/main/java/com/follow/clashx/common/PortalTelemetry.kt:13-25](../android/common/src/main/java/com/follow/clashx/common/PortalTelemetry.kt));
`tunDocument` направляет core error log туда ([XrayPlugin.kt:498-506](../android/app/src/main/kotlin/com/follow/clashx/plugins/XrayPlugin.kt)),
а `awaitAck` зеркалит *каждую* строку `xray.log` в logcat
([731-763](../android/app/src/main/kotlin/com/follow/clashx/plugins/XrayPlugin.kt)).
Подписка управляет outbounds/routing/DNS, хотя inbounds правильно удаляются
([427-486](../android/app/src/main/kotlin/com/follow/clashx/plugins/XrayPlugin.kt)).

**Почему это важно.** Это не удалённая утечка само по себе, и subscription URL
в deep-link path корректно редактируется до host
([lib/common/link.dart:74-82](../lib/common/link.dart)). Однако error/access
сообщения core могут включать адреса узлов, домены и ошибки, сформированные
провайдером; adb/logcat и экспорт диагностических файлов делают их доступными
пользователю с физическим доступом/отладкой. Это следует согласовать с
privacy-text «logs … stay on your device».

**Suggested fix (S).** В production не зеркалировать все core lines в logcat;
использовать allow-list стартовых markers и редактировать URI/IP/credential
patterns. Ограничить размер/ротацию `xray.log` так же, как остальных
telemetry-файлов; явно документировать adb-visible diagnostics.

**Effort:** S.

### m2 — JNI обрабатывает OOM/невалидные строки несимметрично

**Evidence.** `XrayMeasure` проверяет nullable `jstring`, но не результаты
`GetStringUTFChars` для `config`, `tags` и `url`; сразу передаёт их в Go
([`jni_bridge.c:67-80`](file:///Users/saved/.hermes/cache/scratch/xraylib/build/libxray/jni_bridge.c)).
Go затем без nil-check вызывает `C.GoString` для всех аргументов
([`main.go:229-233`](file:///Users/saved/.hermes/cache/scratch/xraylib/build/libxray/main.go)).

**Почему это важно.** При allocation failure JNI возвращает null и оставляет
pending exception; передача null в `C.GoString` не является безопасным
контрактом. Это edge case availability/crash, не обычный subscription path.

**Suggested fix (S).** Проверять каждый результат `GetStringUTFChars`,
освобождать уже полученные строки на error path и возвращать JSON error;
дублировать nil guards в Go export.

**Effort:** S.

## Что проверено и что выглядит корректно

* **Разделение owner/tunnel.** `PortalRuntimeCoordinator` действительно имеет
  один `Mutex`, проверяет generation после async service/child шагов
  ([PortalRuntimeCoordinator.kt:125-289](../android/app/src/main/kotlin/com/follow/clashx/PortalRuntimeCoordinator.kt));
  `onRevoke()` сначала fence-ит generation ([VpnService.kt:136-143](../android/service/src/main/java/com/follow/clashx/service/VpnService.kt)).
  `stopTunLocked` просит child остановиться, очищает только свой epoch и закрывает
  descriptor ([399-424](../android/service/src/main/java/com/follow/clashx/service/VpnService.kt)).
  В рассмотренных путях нет подтверждённого второго reader/утечки fd.
* **Изоляция native instance.** `measureMutex/measureInstance` отделены от
  `coreMutex/coreInstance` ([measure.go:39-44](file:///Users/saved/.hermes/cache/scratch/xraylib/build/libxray/measure.go));
  `XrayMeasureStop` вызывает только `StopMeasure` ([main.go:236-241](file:///Users/saved/.hermes/cache/scratch/xraylib/build/libxray/main.go)).
  Следовательно, штатный `stopMeasure` не может вызвать `XrayStop` туннельного
  core. Новый native sweep корректно закрывает предыдущий measurement instance
  под тем же mutex ([measure.go:84-110](file:///Users/saved/.hermes/cache/scratch/xraylib/build/libxray/measure.go)).
* **Inbound hardening.** Все provider-supplied inbounds заменяются ровно одним
  tun inbound ([XrayPlugin.kt:427-482](../android/app/src/main/kotlin/com/follow/clashx/plugins/XrayPlugin.kt));
  приложение исключает свой UID из VPN при Xray mode
  ([VpnService.kt:312-331](../android/service/src/main/java/com/follow/clashx/service/VpnService.kt)).
  Это устраняет открытый SOCKS/HTTP listener из конфигурации подписки. Подписка
  всё ещё доверена выполнять произвольные поддерживаемые Xray outbounds, routing
  и DNS — это функциональная модель приложения, не новая RCE-находка.
* **Списки и выбор.** `portalShownRows` отвергает live/held group другого
  owner ([lib/providers/state/portal_rows.dart:247-268](../lib/providers/state/portal_rows.dart)),
  а тесты фиксируют это разделение. Сортировка строит rank один раз до sort
  ([portal_controls.dart:1252-1269](../lib/views/dashboard/portal_controls.dart));
  выбранный элемент хранится по profile/mode. Не найдено изменение chips/layout
  в патчах 38–44.
* **Ресурсы.** Child path ограничен 4 workers, чанком 6 и общим deadline 120 s
  ([portal_controls.dart:1706-1717](../lib/views/dashboard/portal_controls.dart)).
  24 узла за ~28 s согласуются с четырьмя последовательными полными прокси
  handshakes на чанк: три вызова по шесть, максимум четыре одновременно. Это
  осознанный компромисс первого результата против contention; сам chunking не
  доказывает лишней работы. Проблема — только отсутствие native max timeout и
  отмены engine path.
